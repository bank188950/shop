# การดำเนินการ, การเชื่อมต่อระบบ และการทดสอบ

## การรันบนเครื่อง local และการ deploy

`README.md` ที่ root เป็นแหล่งข้อมูลหลักในการดำเนินการ การตั้งค่าบนเครื่อง local ตามปกติคือ:

```bash
cd frontend
npm install
npm run dev
```

คัดลอก `backend/.env.example` ไปเป็น `backend/.env`, ตั้งค่าตัวแปร MySQL แล้วเริ่ม document root ของ PHP:

```bash
php -S localhost:8000 -t backend/public
```

frontend ใช้ `http://localhost:5173`; Vite จะ proxy `/api` ไปยังพอร์ต 8000 ใช้ `GET http://localhost:8000/api/health` เพื่อตรวจสอบ entrypoint ของ PHP ปัจจุบัน

สำหรับ shared hosting ของ Apache, README แนะนำให้วิศวกร build `frontend/`, อัปโหลด `frontend/dist/` ไปยัง web root, เปิด `backend/public/api/` เป็น `public_html/api/` และเก็บ `backend/src/`, `backend/.env` และ `backend/storage/` ไว้นอก web root ไฟล์ `frontend/public/.htaccess` จะสงวน `/api/*` ไว้ให้ PHP และส่ง route ของ SPA เช่น `/admin` ไปยัง `index.html`

runbook นี้ดำเนินการตามสถาปัตยกรรมที่อธิบายไว้ใน [สถาปัตยกรรมรันไทม์](architecture/overview.md#การกำหนดเส้นทางคำขอและการ-deploy) โดยไม่ได้กำหนดกระบวนการ import/migration ฐานข้อมูลระดับ production: `database/schema.sql` เป็น schema artifact เดียวที่ตรวจสอบ

## การตั้งค่าและจุดเชื่อมต่อระบบ

| ขอบเขต | แหล่งที่มา | พฤติกรรมปัจจุบัน |
| --- | --- | --- |
| API base ฝั่ง frontend | `frontend/.env.example`, `frontend/src/libs/api.ts` | ค่าเริ่มต้นเป็น `/api`; helper ขอข้อมูลแบบ JSON และโยน error การเชื่อมต่อเป็นภาษาไทยเมื่อ response ไม่ OK ปัจจุบันยังไม่มีฟีเจอร์ใดใช้งาน |
| การกำหนดเส้นทาง API ตอนพัฒนา | `frontend/vite.config.ts` | proxy `/api` ชี้ไปยัง `http://localhost:8000` |
| การตั้งค่า PHP | `backend/.env.example`, `backend/src/bootstrap.php` | environment ให้ค่า `APP_*` และ `DB_*`; ห้าม commit หรือเปิดเผย `backend/.env` ตัวจริง |
| การเข้าถึงฐานข้อมูล | `backend/src/Database/Connection.php` | PDO ใช้ MySQL, UTF-8 MB4, exception, การ fetch แบบ associative และ native prepare |
| พื้นผิว API | `backend/public/api/index.php` | พัฒนาไว้เพียง `GET /health`; route ที่ไม่รู้จักจะคืน JSON 404 |
| ที่จัดเก็บไฟล์ | `backend/storage/products/`, `backend/storage/slips/` | เป็นไดเรกทอรี placeholder เท่านั้น; ไม่พบการพัฒนาการอัปโหลด/ให้บริการไฟล์ |
| ระบบอัตโนมัติของเอกสาร | `.github/workflows/openwiki-update.yml` | การรันอัปเดต OpenWiki แบบ manual หรือทุกวันเวลา 08:00 UTC จะสร้าง PR ของเอกสาร |

โมเดลถาวรที่วางแผนไว้อธิบายอยู่ใน [โมเดล domain](domain-model.md); ฟีเจอร์ที่เริ่มใช้งาน API ควรตัดสินใจ contract ของ request/response อย่างชัดเจนที่นั่น หรือในเอกสาร API ระดับซอร์สโค้ดเมื่อมีการเพิ่ม endpoint

## การตรวจสอบและการทดสอบ

quality gate อัตโนมัติของ frontend ที่ประกาศไว้คือ:

```bash
cd frontend
npm run build
```

คำสั่งนี้จะรัน `tsc -b && vite build` ไม่มี script `test` ใน `frontend/package.json` และไม่พบไฟล์ test/spec ของโปรเจกต์เอง ส่วน Composer ของ PHP ประกาศเพียง PHP 8.2+ และไม่มี test framework ดังนั้น build ที่สำเร็จจึงจำเป็นแต่ยังไม่เพียงพอสำหรับการเปลี่ยนแปลงเชิงธุรกิจ

### การตรวจสอบด้วยมือแบบเจาะจง

| ส่วนที่เปลี่ยน | สิ่งที่ต้องตรวจสอบ |
| --- | --- |
| แคตตาล็อก/ตะกร้าฝั่งลูกค้า | เพิ่มสินค้า, เปลี่ยนจำนวน, โหลดหน้าใหม่ แล้วยืนยันว่ายอดรวมของตะกร้าถูกเก็บไว้ และสินค้าถูกลบเมื่อจำนวนเป็นศูนย์ |
| UI การชำระเงิน | ยืนยันตัวเลือกช่วงจัดส่งทั้งสองแบบ, คำเตือนเมื่อยังไม่ได้เลือกที่จำเป็น, การแสดง QR และต้องไม่มีการอ้างว่ามีการชำระเงิน/สร้างคำสั่งซื้อจริงทั้งที่ยังไม่รองรับ |
| การเตรียมสินค้าฝั่งผู้ดูแล | เลือกคำสั่งซื้อที่จ่ายแล้วในขั้นตอนตรวจสอบซึ่งตรงตามวันที่/ช่วงเวลา, สร้าง batch, นำคำสั่งซื้อที่กำลังเตรียมออก แล้วทำเครื่องหมายว่า batch พร้อมส่ง |
| การจัดส่ง | ยืนยันว่าการดำเนินการตามสถานที่จะเลื่อนเฉพาะคำสั่งซื้อที่พร้อมส่งไปเป็นส่งแล้ว และคงคำสั่งซื้อที่ยังไม่พร้อมไว้ |
| ข้อความตรงฝั่งผู้ดูแล | ส่งข้อความและรูปภาพ, โหลดหน้าใหม่เพื่อดูว่าข้อความถูกเก็บในเครื่อง; อย่าถือว่าไฟล์แนบแบบ object-URL เป็นข้อมูลถาวร |
| การกำหนดเส้นทาง/การ deploy | build SPA; ตรวจสอบว่าการเข้า `/admin/...` โดยตรงถูกจัดการผ่าน fallback ของ Apache ขณะที่ `/api/health` ยังเข้าถึง PHP ได้ |

เงื่อนไขของวงจรการทำงานเบื้องหลังการตรวจสอบการเตรียมสินค้าและการจัดส่งมีบันทึกไว้ใน [คำสั่งซื้อและการจัดส่ง](workflows/orders-and-fulfillment.md#กฎการจัดชุดและการจัดส่งที่กำหนดไว้ใน-store) เมื่อเพิ่มการทดสอบ ให้ให้ความสำคัญกับ unit test ของการเปลี่ยนสถานะ และ integration test ของการสร้างคำสั่งซื้อจากการชำระเงินก่อนการทำ snapshot ของสไตล์

## หมายเหตุด้านการเชื่อมต่อระบบและความปลอดภัย

- **ยังไม่ได้พัฒนาการยืนยันตัวตน** dialog ฝั่งลูกค้าตรวจสอบเฉพาะฟิลด์เท่านั้น; การเข้าสู่ระบบฝั่งผู้ดูแลนำไปยัง `/admin` โดยไม่มีการตรวจสอบฝั่งเซิร์ฟเวอร์หรือ route guard ฟิลด์ password-hash, role และ provider ใน schema เป็นการเตรียมไว้สำหรับอนาคต ไม่ใช่กลไกควบคุมที่ทำงานจริง
- **ยังไม่ได้พัฒนาการชำระเงิน** ค่า QR ฝั่งลูกค้าเป็น placeholder และตัวเลือกการชำระเงินฝั่งผู้ดูแลไม่ได้ถูกเก็บผ่าน operational store ที่ใช้ร่วมกัน อย่าอธิบายว่าทั้งสองเป็นการเชื่อมต่อการชำระเงินจริง
- **สถานะที่เก็บในเบราว์เซอร์ไม่ปลอดภัยสำหรับผู้ใช้หลายคน** ตะกร้า, การเตรียมสินค้า, การตั้งค่าผู้ดูแลในเครื่อง, ผู้ใช้ และข้อความ อาจไม่ตรงกันตามเบราว์เซอร์/อุปกรณ์ URL รูปภาพของข้อความฝั่งผู้ดูแลใช้ `URL.createObjectURL` จึงไม่คงอยู่หลังโหลดหน้าใหม่
- **การอัปโหลดต้องมีการออกแบบฝั่งเซิร์ฟเวอร์** repository จองตำแหน่งจัดเก็บไว้ แต่ยังไม่มีการตรวจสอบการอัปโหลดที่ปลอดภัย, การอนุญาตสิทธิ์, การตั้งชื่อ, กฎการให้บริการไฟล์ และการควบคุมการเข้าถึง
- **การเปลี่ยนสถานะในฐานข้อมูลต้องใช้ API แบบ transaction** การพัฒนาฝั่งเซิร์ฟเวอร์ควรคำนวณยอดคำสั่งซื้อจากข้อมูลที่เชื่อถือได้ และป้องกันการเปลี่ยนสถานะการชำระเงิน, สต็อก และการจัดการคำสั่งซื้อจากการอัปเดตพร้อมกัน

ประเด็นเหล่านี้เป็นช่องว่างเชิงโครงสร้างระหว่าง [สถาปัตยกรรมที่เก็บสถานะในเบราว์เซอร์](architecture/overview.md#ความเป็นเจ้าของสถานะ) กับ [โมเดล MySQL ที่ตั้งใจไว้](domain-model.md#ความไม่ตรงกันระหว่าง-ui-กับ-schema) ไม่ใช่งานเสริมความแข็งแกร่งที่จะทำหรือไม่ก็ได้

## ความคืบหน้าล่าสุดของ repository

commit แรกของโปรเจกต์ได้แนะนำโครง schema/API ส่วน commit ล่าสุดกระจุกอยู่ที่ workspace ผู้ดูแลฝั่ง frontend ได้แก่ การปรับ preparation-board/สถานะ/ตัวกรอง, UI รายละเอียดคำสั่งซื้อ, UI รีเซ็ตสต็อก และล่าสุดคือการส่งข้อความตรงจากผู้ดูแล (`f2b2383`) ตามด้วยการปรับขนาดไอคอนข้อความเล็กน้อย (`ee387d0`) ประวัติ git จึงสนับสนุนการมองผลิตภัณฑ์ปัจจุบันว่าเป็นต้นแบบ UI ที่กำลังพัฒนาอยู่ ขณะที่การเก็บข้อมูลฝั่ง backend และการเชื่อมต่อแบบ end-to-end ยังเป็นงานในอนาคต
