# การตรวจสอบสลิปโอนเงินด้วย Slip2Go

เอกสารนี้เป็นแหล่งอ้างอิงเดียวของการเชื่อมต่อ Slip2Go สำหรับยืนยันการชำระเงินของคำสั่งซื้อ หากขัดกับโค้ด ให้แก้ทั้งสองฝั่งในการเปลี่ยนแปลงเดียวกัน

## ภาพรวมของ flow

1. ลูกค้ากดยืนยันคำสั่งซื้อ ระบบสร้างออเดอร์สถานะ `pending_payment` และตัดสต็อกทันที
2. หน้าสรุปคำสั่งซื้อแสดง QR PromptPay พร้อมยอดที่ต้องชำระ **QR สร้างเองในโปรเจกต์ ไม่เรียก API ของ Slip2Go** เพราะโควตา `สร้าง QR รับเงิน` มีเพียง 80 ครั้งต่อแพ็กเกจ
3. ลูกค้าโอนเงินแล้วอัปโหลดรูปสลิป
4. Backend บันทึกไฟล์ลง `backend/storage/slips/` แล้วส่งไปตรวจกับ Slip2Go
5. ผ่าน — อัปเดต `orders.payment_status = 'paid'` และ `orders.order_status = 'pending_review'` ในทรานแซกชันเดียวกับการบันทึกข้อมูลสลิป
6. ไม่ผ่าน — คงสถานะ `pending_payment` ไว้ แสดง popup ภาษาไทยบอกสาเหตุ และบันทึกผลตรวจไว้ให้ผู้ดูแลตรวจย้อนหลังได้

ปุ่ม `ชำระเงินแล้ว` แบบกดยืนยันเองถูกแทนที่ด้วยช่องอัปโหลดสลิป ปุ่มเดิมเปิดให้ผู้ใช้ตั้งสถานะคำสั่งซื้อของตัวเองเป็นจ่ายแล้วได้โดยไม่มีหลักฐาน

## การยืนยันตัวตนและปลายทาง

- Base URL คือ `https://connect.slip2go.com` เก็บใน `backend/.env` คีย์ `SLIP2GO_BASE_URL` และต้องเป็น `https` เท่านั้น เพราะ header มี secret
- Secret Key เก็บใน `backend/.env` คีย์ `SLIP2GO_API_KEY` ห้าม commit และห้ามส่งไปฝั่ง client
- ทุก request ส่ง header `Authorization: Bearer <SLIP2GO_API_KEY>` และ `Content-Type` ตามแต่ละ endpoint
- ตั้ง IP Whitelist ได้ที่หน้า `API Connect` ของ Slip2Go เป็นตัวเลือกไม่บังคับ ควรใส่ IP ของ server จริงตอนขึ้น production
- บัญชีรับเงินของร้านเก็บในตาราง `settings` แถว `id = 1` ไม่เก็บใน `.env` และไม่ hardcode ในโค้ด เพื่อให้เปลี่ยนบัญชีได้โดยไม่ต้อง deploy ใหม่ ใช้คอลัมน์ `payment_account_name` (ข้อความแสดงใต้ QR), `payment_promptpay_type` (`msisdn` หรือ `natid`) กับ `payment_promptpay_id` (ปลายทางที่ฝังใน QR), `payment_account_number` (เลขบัญชีตัวเลขล้วน ส่งเป็น `checkReceiver.accountNumber`), `payment_bank_code` และ `payment_slip_account_type` (ค่า `accountType` ที่ส่งให้ Slip2Go)
- ปลายทางใน QR แยกจากค่าที่ใช้ตรวจสลิป QR ใช้พร้อมเพย์เพราะแอปธนาคารต้องสแกนได้ ส่วนการตรวจสลิปใช้เลขบัญชีเพราะแม่นกว่าการเทียบชื่อ ทั้งสองทางเงินเข้าบัญชีเดียวกัน
- ตรวจการเชื่อมต่อได้โดยเรียก `GET /api/account/info` ซึ่งไม่เสียโทเคน คำตอบที่ถูกต้องคือ `code` เท่ากับ `200001` พร้อมข้อมูล `tokenRemaining` และ `estimatedQuotaSlip`

## Endpoint ที่โปรเจกต์นี้ใช้

| งาน | Method | Path | หมายเหตุ |
| --- | --- | --- | --- |
| ตรวจสลิปด้วยรูปภาพ | POST | `/api/verify-slip/qr-image/info` | ตัวหลัก เสีย 0.250 โทเคนต่อครั้ง |
| ดึงข้อมูลบัญชี | GET | `/api/account/info` | ไม่เสียโทเคน ใช้ตรวจการเชื่อมต่อและเฝ้าดูโทเคนคงเหลือ |
| ดึงข้อมูลสลิปเก่า | GET | ตามเอกสาร Slip2Go | อ่านผลตรวจเดิมด้วย `referenceId` โดยไม่เสียโทเคนซ้ำ |

Endpoint ที่ตั้งใจไม่ใช้ ได้แก่ ตรวจด้วย QR-Code (ต้องถอด QR จากรูปเองซึ่งพังง่ายเมื่อรูปเบลอ), Base64 (ขนาด request โตขึ้นโดยไม่ได้ประโยชน์), Image URL (ต้องเปิดรูปสลิปของลูกค้าให้เข้าถึงจากอินเทอร์เน็ต) และสร้าง QR PromptPay ทั้งสองแบบ (กินโควตา 80 ครั้ง)

## Request ของการตรวจสลิปด้วยรูปภาพ

ส่งเป็น `multipart/form-data` สองส่วน

| key | ชนิด | บังคับ | รายละเอียด |
| --- | --- | --- | --- |
| `file` | File | ใช่ | รูปสลิป รับ png, jpg, jpeg |
| `payload` | JSON string | ไม่ | เงื่อนไขการตรวจ |

โครงของ `payload` ที่โปรเจกต์นี้ส่งทุกครั้ง

| key | ชนิด | ค่าที่ใช้ |
| --- | --- | --- |
| `checkReceiver` | Array | ทุกปลายทางของร้าน ได้แก่ เลขบัญชีพร้อม `accountType` และเบอร์พร้อมเพย์ทั้งแบบ 10 หลักและแบบ 13 หลักที่มีรหัสประเทศ |
| `checkAmount.type` | String | `eq` |
| `checkAmount.amount` | String | ยอด `orders.total_amount` ไม่ใส่ทศนิยมและไม่ใส่ลูกน้ำ เช่น `35` |

ข้อบังคับของแต่ละค่า

- **ต้องส่ง `payload` ทุกครั้ง** ถ้าไม่ส่ง Slip2Go จะตรวจเพียงว่าสลิปมีอยู่จริงในระบบธนาคารและคืน `200000` โดยไม่เทียบยอดหรือบัญชีปลายทาง ทำให้สลิปของรายการอื่นผ่านได้
- `checkReceiver` เป็น array ที่ใช้ตรรกะ **หรือ** คือตรงเงื่อนไขอย่างน้อยหนึ่ง object ก็ถือว่าถูกต้อง จึงส่งทุกปลายทางของร้านไปให้ครบ เพราะสลิประบุผู้รับตามช่องทางที่ลูกค้าโอนมา สแกน QR พร้อมเพย์จะได้เบอร์ ส่วนการพิมพ์เลขบัญชีโอนเองจะได้เลขบัญชี ทุกค่าที่ส่งเป็นปลายทางของร้านเองทั้งหมด การตรงกับค่าใดค่าหนึ่งจึงยืนยันได้ว่าเงินเข้าร้านจริง
- ฟิลด์ภายใน object เดียวกันถูกตรวจแบบ **และ** จึงไม่ใส่ `accountType` ให้ปลายทางพร้อมเพย์ เพราะยังไม่รู้ว่ารหัสประเภทของพร้อมเพย์คืออะไร การใส่ผิดจะทำให้ object นั้นไม่ตรงทั้งชุด
- **ไม่ส่ง `checkDuplicate`** เพราะ Slip2Go นับสลิปที่เคยส่งไปตรวจว่าซ้ำ แม้ครั้งนั้นจะตรวจไม่ผ่าน ทำให้สลิปที่ติดเงื่อนไขรอบแรกเอาไปใช้กับคำสั่งซื้อที่ถูกต้องไม่ได้อีก ระบบกันสลิปซ้ำด้วย unique key ของ `slip_trans_ref` ที่เราคุมเองแทน
- `checkAmount.type` ต้องเป็น `eq` การใช้ `gte` จะทำให้ยอดที่โอนเกินผ่านและทำให้ยอดในระบบไม่ตรงกับบัญชี
- `accountType` ของธนาคารกรุงเทพคือ `01002` รูปแบบนี้ต่างจาก `bank.id` ที่ response คืนมาซึ่งเป็นรหัสธนาคารสามหลัก
- `accountNumber` ห้ามเว้นวรรคหรือใส่สัญลักษณ์
- ไม่ใช้ `accountNameTH` และ `accountNameEN` เพราะการเทียบชื่อเปราะและเอกสารกำหนดว่าห้ามใส่คำนำหน้า
- ไม่ใช้ `checkDate` เพราะโปรเจกต์นี้ไม่ยกเลิกคำสั่งซื้อที่ไม่ชำระเงินอัตโนมัติ จึงไม่มีกรอบเวลาที่ต้องบังคับ

## Response และการเก็บข้อมูล

ข้อมูลอยู่ใน `data` ของ response โดยฟิลด์ที่โปรเจกต์นี้เก็บลง `order_payments` เป็นดังนี้

| ฟิลด์ใน response | คอลัมน์ | เหตุผล |
| --- | --- | --- |
| `data.referenceId` | `slip_reference_id` | ใช้เรียกดูผลตรวจเดิมโดยไม่เสียโทเคน |
| `data.transRef` | `slip_trans_ref` | เลขอ้างอิงธุรกรรมของธนาคาร ใช้เป็นกุญแจกันสลิปซ้ำ **บันทึกเฉพาะตอนตรวจผ่าน** เพราะคอลัมน์นี้มี unique key ถ้าจองไว้ตอนตรวจไม่ผ่าน สลิปใบเดิมจะเอาไปใช้กับคำสั่งซื้อที่ถูกต้องไม่ได้อีก |
| `data.dateTime` | `slip_transferred_at` | เวลาที่โอนจริง เป็นเวลา GMT ต้องแปลงเป็น `Asia/Bangkok` ก่อนบันทึก |
| `data.amount` | `slip_amount` | ยอดที่โอนจริง เป็นตัวเลข ไม่ใช่ string |
| `data.sender.account.name` | `slip_sender_name` | ใช้ค้นหาสลิปเมื่อลูกค้าสอบถาม |
| `data.sender.bank.name` | `slip_sender_bank` | ประกอบการตรวจสอบ |
| `data.sender.account.bank.account` | `slip_sender_account` | เลขบัญชีผู้โอนแบบปิดบัง |
| `data.receiver.account.bank.account` หรือ `data.receiver.account.proxy.account` | `slip_receiver_account` | บันทึกเป็น snapshot เพราะบัญชีร้านเปลี่ยนได้ในอนาคตแต่บิลเก่าต้องไม่เปลี่ยนตาม สลิปที่โอนผ่านพร้อมเพย์ไม่มี `bank.account` จึงต้องอ่าน `proxy.account` สำรอง |
| `code` | `verify_code` | ใช้ตรวจสอบย้อนหลังว่าเหตุใดจึงผ่านหรือไม่ผ่าน |
| `message` | `verify_message` | ประกอบการแก้ปัญหา |

เลขบัญชีทั้งฝ่ายผู้โอนและผู้รับที่ response คืนมาถูกปิดบังอยู่แล้ว เช่น `xxx-x-x5366-x` จึงเก็บได้ตามที่ได้รับ

## การตีความ response code

`code` เป็น string และ **ผลตรวจที่ไม่ผ่านหลายกรณีคืน HTTP 200** จึงต้องอ่านค่า `code` เสมอ ห้ามตัดสินจาก HTTP status เพียงอย่างเดียว

| code | ความหมาย | การจัดการในระบบ |
| --- | --- | --- |
| `200000`, `200200` | สลิปถูกต้องตามเงื่อนไขที่ส่งไป | อัปเดตเป็น `paid` และ `pending_review` |
| `200404` | ไม่พบข้อมูลสลิป | ปฏิเสธและแจ้งลูกค้าให้ตรวจสอบรูปที่อัปโหลด |
| `200500` | สลิปเสียหรือสลิปปลอม | ปฏิเสธ |
| `200501` | สลิปซ้ำ | ปฏิเสธและแจ้งว่าสลิปนี้ถูกใช้แล้ว |
| `200401` | บัญชีผู้รับไม่ถูกต้อง | คงสถานะเดิมและรอผู้ดูแลตรวจ ไม่ปฏิเสธอัตโนมัติ |
| `200402` | ยอดโอนไม่ตรงเงื่อนไข | คงสถานะเดิมและรอผู้ดูแลตรวจ เพราะการโอนขาดหรือเกินต้องมีคนตัดสิน |
| `200403` | วันที่โอนไม่ตรงเงื่อนไข | คงสถานะเดิมและรอผู้ดูแลตรวจ |
| `200502`, `429000`, `500500` | ระบบธนาคารหรือ Slip2Go มีปัญหา | คงสถานะเดิม แจ้งลูกค้าให้ลองใหม่ ไม่นับเป็นความผิดของลูกค้า |
| `400001` ถึง `400422` | request ไม่ถูกต้อง | เป็นข้อผิดพลาดฝั่งเรา บันทึก log และแจ้งลูกค้าเป็นข้อความทั่วไป |
| `401001` ถึง `401007` | ปัญหาการยืนยันตัวตน แพ็กเกจ โทเคน เครดิต หรือ IP | คงสถานะเดิม รอผู้ดูแลตรวจ และแจ้งเตือนผู้ดูแลทันที ห้ามปฏิเสธลูกค้าเพราะเป็นความผิดฝั่งเรา |

`401004` แพ็กเกจหมดอายุ และ `401005` โทเคนหมด จะทำให้ลูกค้าทุกรายตรวจสลิปไม่ผ่านพร้อมกัน จึงต้องเฝ้าดูโทเคนคงเหลือผ่าน `/api/account/info` และแจ้งเตือนในส่วนผู้ดูแลก่อนโทเคนหมด

## การควบคุมต้นทุนและการกดซ้ำ

- ตรวจชนิดและขนาดไฟล์ที่ฝั่ง client ก่อนส่งทุกครั้ง คำขอที่ไม่ผ่านการตรวจนี้ไม่ถูกส่งออกไปและไม่นับเป็นการพยายาม
- จำกัดการเรียก API ไม่เกิน **3 ครั้งต่อคำสั่งซื้อ** นับที่ `order_payments.verify_attempts` เกินกว่านั้นให้ติดต่อผู้ดูแลเพื่อตรวจด้วยตาซึ่งไม่เสียโทเคน
- ปิดปุ่มระหว่างรอผลและกันการยิงซ้ำที่ฝั่ง server ด้วย ไม่พึ่งสถานะของ UI เพียงอย่างเดียว เพราะการกดซ้ำเสียโทเคนเพิ่มและอาจได้ `400409`
- `order_payments.slip_trans_ref` มี unique key เป็นด่านกันสลิปซ้ำชั้นที่สองของระบบเราเอง

## ข้อจำกัดที่ยังไม่ได้ตรวจสอบกับของจริง

- การส่ง `checkReceiver.accountNumber` เป็นเลขบัญชีเพียงค่าเดียว **ใช้ไม่ได้กับการโอนผ่านพร้อมเพย์** ทดสอบจริงแล้วได้ `200401` และ `receiver.account.bank.account` ไม่มีค่า เพราะสลิประบุผู้รับเป็น proxy จึงต้องส่งเบอร์พร้อมเพย์ไปใน array ด้วย
- การส่งเบอร์พร้อมเพย์แบบ 10 หลักและ 13 หลักที่มีรหัสประเทศ ทดสอบแล้วยังได้ `200401` เช่นกัน
- ธนาคารปิดบังปลายทางบนสลิปเหลือเห็น 4 ตัวท้าย เช่นเบอร์ `083-029-1314` มาเป็น `xxx-xxx-1314` และตัวอย่างในเอกสาร Slip2Go คือ `xxxxxx1234` ซึ่งเป็นรูปแบบปิดบังที่ตัดสัญลักษณ์ออกแล้ว จึงส่งรูปแบบ `xxxxxx` ต่อด้วยสี่ตัวท้ายไปเทียบเพิ่ม ยังรอผลทดสอบ
- หากรูปแบบปิดบังยังไม่ผ่าน ทางเลือกถัดไปคือไม่ส่ง `checkReceiver` แล้วเทียบเองจากค่าที่ response คืนมา ซึ่งเทียบได้เพียงสี่ตัวท้ายเพราะที่เหลือถูกปิดบัง ต้องยอมรับว่าอ่อนกว่าการเทียบเต็มเลข
- ยังไม่ยืนยันรหัส `accountType` ของปลายทางพร้อมเพย์ ปัจจุบันจึงไม่ส่งฟิลด์นี้ไปกับ object ของพร้อมเพย์
- ความหมายของ `01` ที่นำหน้า `accountType` เป็นการอนุมานว่าเป็นรหัสประเภทบัญชี ยังไม่มีเอกสารยืนยัน
- รูปแบบของ `checkAmount.amount` เมื่อยอดมีเศษสตางค์ยังไม่ยืนยัน ปัจจุบันราคาสินค้าของร้านเป็นจำนวนเต็มจึงยังไม่กระทบ
- ปลายทางของ QR แบบเลขบัญชีธนาคาร (tag 29 sub-tag 04) **ใช้ไม่ได้** ทดสอบกับแอป SCB แล้วขึ้นว่าอ่าน QR ไม่ได้ ทั้งที่ payload ถูกตามมาตรฐานและ CRC ถูก จึงเปลี่ยนมารองรับเฉพาะเบอร์โทร (sub-tag 01) และเลขบัตรประชาชนหรือเลขนิติบุคคล (sub-tag 02) เท่านั้น ห้ามใส่ปลายทางแบบเลขบัญชีกลับเข้าไปอีก
- ยังต้องทดสอบสแกน QR แบบพร้อมเพย์ด้วยแอปธนาคารจริงหลายค่ายก่อนเปิดใช้งาน
- ยังไม่ได้ทดสอบการตรวจสลิปด้วยสลิปจริง เพราะต้องมีการโอนเงินจริงหนึ่งรายการก่อน
